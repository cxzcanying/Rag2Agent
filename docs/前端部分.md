## 2. 为什么聊天接口使用 POST + SSE，而不是 EventSource？

**参考回答：**

聊天请求需要提交 `query`、`kbId` 等请求体，还需要携带 `satoken` 鉴权头。浏览器原生 `EventSource` 主要面向 GET，请求方法、请求体和自定义请求头受到限制，因此项目使用 `fetch` 发送 POST，再通过 `response.body.getReader()` 消费服务端返回的 `text/event-stream`。

这种方案同时满足：

1. POST 提交复杂请求参数；
2. 携带自定义鉴权头；
3. 服务端持续推送引用、工具状态、审批和最终答案；
4. 浏览器可以主动取消请求或处理异常状态码。

## 3. 后端发送的 SSE 数据是什么格式？为什么每次都要 flush？

**参考回答：**

项目手动按 SSE 协议写响应：

```text
event:message
data:{"type":"reference","data":[...]}

event:message
data:{"type":"done","data":{"answer":"..."}}

```

`event:` 表示事件名称，`data:` 承载 JSON 数据，空行表示一个 SSE 事件结束。每次写完调用 `flush()`，是为了立即把事件发送给浏览器，避免数据继续留在 Servlet 或代理缓冲区中。

昨天的代码由错误的同步 `SseEmitter` 用法改成 `HttpServletResponse + PrintWriter`。原因是原实现还没正常返回 emitter 就完成了全部同步处理，浏览器可能收到部分数据却得不到正常的流结束信号，最终表现为页面一直 loading。

## 4. 为什么不能对每次 reader.read() 的 value 直接 JSON.parse？

**参考回答：**

`reader.read()` 返回的是网络分片，不是完整 SSE 事件，也不保证正好对应一个 JSON 对象。一个 JSON 可能被拆成多个分片，多个事件也可能合并在同一个分片中。

因此项目维护 `buffer`：

1. 新分片通过 `TextDecoder` 转成字符串并追加到 `buffer`；
2. 按换行拆分；
3. 最后一段可能还没结束，重新保留到 `buffer`；
4. 只有完整的 `data:` 行才进行 `JSON.parse`。

面试中的关键结论是：**TCP/HTTP 分片边界、SSE 事件边界和 JSON 对象边界不是一回事。**

**代码出处：**

- `web/src/api.js:55-77`

## 5. TextDecoder 的 stream: true 有什么作用？

**参考回答：**

UTF-8 中文字符可能由多个字节组成，而网络可能把这些字节拆到不同分片。如果每个分片独立解码，可能产生乱码或替换字符。

`decoder.decode(value, { stream: true })` 会保留当前分片末尾未完成的字符字节，等下一分片到达后继续解码。因此它解决的是字符字节跨分片问题，`buffer` 解决的是 SSE 行和 JSON 跨分片问题，两者职责不同。

## 6. 为什么 AI 对话接口要设计结构化事件，而不是只返回文本？

**参考回答：**

Agent 执行不是简单的“请求进去、字符串出来”，中间可能发生检索、工具调用、等待审批和异常。项目使用统一的 `AgentEvent(type, data)` 表达过程状态：

| 事件 | 含义 | 前端处理 |
|---|---|---|
| `reference` | 初始检索完成 | 展示文档和切块引用 |
| `tool_start` | 开始执行只读工具 | 展示过程提示 |
| `approval_required` | 高风险工具等待人工确认 | 展示批准、拒绝按钮 |
| `done` | Agent 完成 | 写入最终答案和引用 |
| `error` | 执行失败 | 显示错误并结束等待状态 |

SSE 只解决“如何持续传输”，结构化事件解决“传输什么业务状态”。事件协议可以让后端状态机和前端展示解耦，也便于未来增加 token、步骤耗时、成本等事件。

## 7. Human-in-the-loop 审批链路是怎样工作的？

**参考回答：**

当模型请求调用 `delete_document` 时，后端不会立即执行：

1. 写入 `tool_call`，状态设为 `WAITING_APPROVAL`；
2. 将 `agent_run` 设为 `WAITING_APPROVAL`；
3. 把消息历史和引用暂存 Redis；
4. 通过 SSE 发送 `approval_required`，其中包含 `runId`、`toolCallId`、`toolName` 和 `arguments`；
5. 前端展示工具名、参数以及批准/拒绝按钮；
6. 用户操作后，前端调用 `/api/agent/approvals/{runId}`；
7. 后端恢复 Redis 中的上下文，执行或拒绝工具，再继续模型循环。

`runId` 标识整次 Agent 执行，用于恢复任务；`toolCallId` 标识某一次工具调用，用于审计，二者不能混用。

## 8. 为什么审批接口需要 CAS？

**参考回答：**

用户可能双击按钮，两个浏览器也可能同时审批同一个 `runId`。如果采用“先查询状态，再执行工具”，两个请求可能同时读取到 `WAITING_APPROVAL`，最终重复删除文档。

项目通过条件更新抢占执行权：只有状态仍为 `WAITING_APPROVAL` 时才能更新为 `EXECUTING`。第一个请求更新成功，后续请求影响行数为 0，直接拒绝。

这对 Agent 特别重要：只读工具重复执行通常只是浪费模型额度，但删除、发邮件、转账等副作用工具重复执行会造成真实业务事故。

## 9. 文档上传成功后，为什么还要轮询状态？

**参考回答：**

上传接口只表示文件和任务创建成功。真正可检索前，还要经过 RocketMQ 消费、解析、切块、Embedding 和 pgvector 写入，因此“上传成功”不等于“入库完成”。

前端每 3 秒重新查询文档列表：存在 `UPLOADED` 或 `INDEXING` 时继续轮询；全部进入 `INDEXED` 或 `FAILED` 后停止。组件卸载时也必须清理定时器，避免无效请求和资源泄漏。

状态含义：

```text
UPLOADED -> 已上传，等待处理
INDEXING -> 正在解析、切块或生成向量
INDEXED  -> 已入库，可以检索
FAILED   -> 入库失败
```

轮询只是前端展示方式，后端仍需要保证任务状态机、幂等和失败处理。任务规模更大或实时性要求更高时，可以演进为 SSE/WebSocket 推送任务状态。

## 10. 为什么流式接口容易漏掉鉴权？

**参考回答：**

普通 JSON 请求通常经过统一请求封装自动添加 token，但流式聊天为了手动读取 `ReadableStream`，使用了独立的 `fetch`。如果不单独添加 `satoken`，就会出现普通接口正常、聊天接口 401 的问题。

项目在 `agent.chat` 中重新读取 token 并加入请求头。后端还应继续校验：

1. `kbId` 是否属于当前用户；
2. `documentId` 是否属于用户可操作的知识库；
3. `runId` 是否属于当前用户；
4. 当前用户是否有权批准对应工具。

当前项目只完成了登录鉴权，资源归属 ACL 尚未完整落地。

## 11. SSE 的 done、error 和连接结束应该怎样区分？

**参考回答：**

业务完成、业务失败和网络断开是三类不同结果：

- `done`：Agent 正常完成，由业务事件明确通知；
- `error`：后端捕获业务异常，通过 SSE 事件返回；
- `reader.read().done=true`：HTTP 响应流结束，只说明连接结束，不一定代表业务成功。

因此前端不能把“连接关闭”直接等同于“回答成功”，应以 `done/error` 业务事件作为最终状态，同时对异常断连设置错误提示或重试策略。

当前代码已经处理 `done/error`，但还没有实现断线重连、超时、用户取消和“连接结束但没有终态事件”的校验。

## 12. Vue 响应式问题为什么会导致“后端有答案，页面却不更新”？

**参考回答：**

SSE 回调会异步修改 assistant 消息。如果在 `push` 前保存普通对象引用，随后一直修改这个原始对象，可能绕过 Vue 放进响应式数组后的代理对象，导致页面更新和 `localStorage` 深度监听不完整。

昨天的修复方式是先把对象放进 `messages.value`，再从数组中取回响应式代理：

```javascript
messages.value.push({ role: 'assistant', content: '', references: [] })
const assistant = messages.value[messages.value.length - 1]
```

面试不需要深入 Vue 源码，但应该知道：流式回调修改的数据必须属于前端响应式状态，否则后端链路正确也可能表现为页面无结果。

## 13. 当前实现还有哪些不足？

**参考回答：**

1. SSE 解析只按单行 `data:` 处理，没有实现多行 data 聚合；
2. 没有断线重连、超时和 `AbortController` 主动取消；
3. 没有校验“流结束前是否收到 done/error”；
4. 审批后的继续执行使用普通 JSON 返回，与初始 SSE 协议不完全统一；
5. 对话历史只保存在 `localStorage`，不能跨设备，也不适合敏感数据；
6. `kbId/documentId/runId` 的用户归属校验尚未完整实现；
7. 只读工具调用没有完整落库审计。

面试时不要只说“项目已经支持 SSE 和审批”，还要能说明当前边界以及下一步演进方案。

## 14. 一分钟面试总结

> 项目的聊天接口使用 fetch POST 携带问题、知识库 ID 和鉴权信息，通过 ReadableStream 消费 SSE。前端用 TextDecoder 和 buffer 处理字符及网络分片，再根据 reference、tool_start、approval_required、done、error 等结构化事件更新界面。高风险工具不会直接执行，Agent 进入 WAITING_APPROVAL 并把上下文暂存 Redis；用户通过 runId 审批后，后端使用 CAS 防止重复处理，恢复上下文并继续模型循环。文档上传则是 RocketMQ 异步入库，前端轮询任务状态直到 INDEXED 或 FAILED。当前还需要补充完整 SSE 状态机、断线处理、资源 ACL 和工具审计。
