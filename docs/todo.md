## 三、已确认并实现的轻量方案

以下七项方案已完成实现；同一小节中的其他选项保留为后续升级参考。

### 3.1 `A1` SSE 断线恢复协议

**当前实现**：Redis Stream 保存结构化 SSE 事件，客户端使用 `Last-Event-ID` 请求缺口，服务端按 run 权限回放增量事件。

- [x] 每个 run 的 SSE 事件持久化 `eventId`，断线后只返回断点之后的事件；实时事件与异常事件走同一持久化路径。
- [x] `/api/agent/runs/{runId}/events` 支持 `Last-Event-ID`，前端记录最后事件 ID 并调用回放接口。

保留窗口由 Redis Stream TTL 控制，超出窗口时客户端仍可通过 run 状态接口获得最终结果。

### 3.2 `A2` 动态配置

**当前边界**：单实例内可热更新白名单配置，重启后恢复 YAML，多实例同步和灰度发布仍需配置中心。

**已实现：本地 YAML + 管理接口（A2-L）**

- [x] 白名单运行时配置、版本号、边界校验和更新日志已落地；重启后恢复 YAML 默认值。

- 新增 `RuntimeConfigService` 和 `/api/runtime-config` 管理接口，内存快照覆盖 YAML 默认值。
- 仅允许限流、检索超时、Agent 上下文预算及输入输出边界等白名单配置，变更带版本号并写结构化更新日志；重启后回到 YAML。
- 优点：不增加外部组件，开发和部署最简单；配置变更链路清晰，适合当前单机 Demo。
- 缺点：多实例之间不会自动同步；重启后配置恢复默认，不能提供真正的发布、灰度和回滚能力。
- 适用：本地开发、单实例部署、临时调参和演示环境。
- 实现代价：低到中，集中在配置快照、白名单校验、版本记录和管理接口。

**生产选项：配置中心（A2-C）**

- 接入 Nacos/Apollo，支持发布、灰度、回滚和多实例同步。
- 优点：具备多实例同步、版本发布、灰度、回滚和变更审计能力，适合生产集群。
- 缺点：引入新的基础设施、权限体系和可用性依赖；本地开发、测试和故障排查复杂度上升。
- 适用：多实例生产环境、频繁调参、需要配置审批和灰度发布的场景。
- 实现代价：中到高，需要选定配置中心并补充 Docker、权限、启动顺序和回滚演练。

### 3.3 `A3` Token 计数与成本估算

**当前边界**：上下文预算仍使用字符估算；账本已按供应商实际 usage 和官方分时价格计算，tool schema 的 tokenizer 偏差仍需更多真实样本校准。

**已实现：provider/model Token 与静态价格表（A3-S）**

- [x] 已记录 provider/model 的实际 usage token、字符估算 token，并按官方价格配置输出成本指标；DeepSeek 工作日 peak/off-peak 自动切换，SiliconFlow 当前 BGE 模型按官方免费价记录。

- `TokenCostService` 按 provider/model 记录供应商返回的实际 usage，并按字符数估算请求 token。
- 价格从 YAML 的 provider/model 配置读取；未配置价格时只记录 token，不伪造金额。
- 优点：数据模型和依赖都轻量，能较快获得可解释的 token/成本数据；provider 数量少时维护成本低。
- 缺点：价格调整需要改配置并发布；tokenizer 仍可能因 provider 差异产生偏差，无法自动处理复杂计费规则。
- 适用：当前项目的少量 provider、单体部署和研发阶段成本观测。
- 实现代价：中，需要抽象 tokenizer、增加账本字段和补充价格配置及测试。

**数据化选项：数据库价格表（A3-D）**

- 增加模型价格表和生效时间，账本按价格版本计算成本。
- 优点：价格可由运营按生效时间调整，支持历史账本重算、多币种或不同计费规则扩展。
- 缺点：增加数据库迁移、管理接口、权限控制和价格版本冲突处理；数据模型更重。
- 适用：模型数量多、价格变化频繁、需要财务对账或多团队分摊成本的场景。
- 实现代价：中到高，除 tokenizer 和账本外还要建设价格管理闭环。

### 3.4 `A4` 统一 API 幂等键

**当前边界**：知识库创建和文档上传已统一使用 `Idempotency-Key`，其他副作用接口仍需逐一接入。

**已实现：按接口定义 `Idempotency-Key`（A4-K）**

- [x] 知识库创建、文档上传已接入参数指纹、处理中保护、成功响应重放和失败释放；上传指纹包含文件 SHA-256。

- 仅对创建/有副作用接口启用；以 `owner + endpoint + key` 建幂等记录，参数指纹不一致返回 400。
- 上传接口额外保存文件 checksum；相同 key 重放返回第一次结果，不重复发消息。
- 幂等记录按 24 小时窗口清理，处理中请求返回稳定错误，成功请求保存响应快照。
- 优点：语义完整，能覆盖网络重试、客户端超时和消息重复；参数指纹能阻止同一 key 被错误复用。
- 缺点：需要新增幂等记录、唯一约束、结果快照和清理策略；文件上传要处理对象存储与数据库的一致性。
- 适用：对创建、上传、扣费或异步任务重复执行敏感的生产 API。
- 实现代价：中，需要逐个梳理接口返回值和失败恢复语义。

**简化选项：仅 checksum 复用（A4-H）**

- 只按 `kbId + file checksum` 复用或创建新版本，不引入通用幂等表。
- 优点：实现快、数据结构简单，能有效减少相同文件重复上传和重复入库。
- 缺点：只覆盖文件内容，不覆盖创建知识库、评测任务等非文件请求；同一内容的不同业务意图无法区分。
- 适用：当前只想解决重复上传，且暂不承诺全 API 幂等的场景。
- 实现代价：低，但后续扩展到通用幂等时可能需要迁移。

### 3.5 `A5` 检索并行池背压

**当前边界**：向量/关键词召回队列满时快速失败，线程池容量和 P95 仍需真实压测校准。

**已实现：快速失败（A5-R）**

- [x] 检索并行线程池拒绝时返回稳定繁忙错误并记录 `rag2agent.search.retrieval.rejected` 指标。

- 不扩大线程池，避免高峰期把数据库和模型服务拖垮。
- 优点：行为确定、保护下游最有效，线程池和数据库负载容易控制，故障可以快速暴露。
- 缺点：高峰期部分请求会直接失败，用户需要重试；对突发流量的容错能力较弱。
- 适用：请求可重试、优先保证系统不雪崩的生产服务。
- 实现代价：低，只需捕获拒绝异常、统一 503 响应和指标。

**降级选项：队列满时串行执行（A5-S）**

- 先执行向量召回，再补关键词召回；延迟更高但成功率更高。
- 优点：队列满时仍有机会完成请求，用户感知的失败率更低。
- 缺点：串行路径延迟更高，可能导致请求堆积；总超时、取消和结果标记逻辑更复杂。
- 适用：读请求优先、延迟可接受且召回成功率比尾延迟更重要的场景。
- 实现代价：中，需要扩展超时策略和降级指标。

### 3.6 `A6` 提示注入风险信号

**当前边界**：已对常见注入模式做规则标记，复杂语义变体仍需分类模型和样本评测。

**已实现：规则引擎仅标记（A6-R）**

- [x] Agent 输入命中注入规则时记录指标并发送 `security` SSE 事件，不替代权限控制。

- 无新增模型调用，误报可控，不能替代 ACL。
- 优点：零模型成本、低延迟、易解释，适合作为安全观测和后续治理的数据入口。
- 缺点：只能覆盖已知模式，容易漏报和误报；不能单独判断复杂的语义攻击。
- 适用：先建立风险基线、需要保守上线、不希望影响正常问答的场景。
- 实现代价：低到中，主要是规则配置、脱敏日志、指标和测试集维护。

**增强选项：分类模型（A6-M）**

- 使用独立分类模型判断风险并决定拦截/降级。
- 优点：对变体表达和复杂语义的识别能力更强，可按风险等级执行拦截、降级或人工审核。
- 缺点：增加模型成本和延迟，引入新的可用性依赖；误判会直接影响用户请求，需要持续评测。
- 适用：有稳定攻击样本、明确安全策略和专门安全运营能力的生产环境。
- 实现代价：高，需要模型选型、样本标注、阈值校准和故障降级。

### 4.4 代码层面已确认的边界（面试评审提炼，已定位到实现）

以下为通读代码时确认的真实缺口，不是"预留重构"。前 3 项本次已修复并通过 `mvn -pl bootstrap -am test` 定向验证；其余为架构/运维口径，不改语义。

- [x] Agent 审批超时自动终态化：`agent_run` 会一直停在 `WAITING_APPROVAL`，唯一兜底是 Redis 上下文 30 分钟 TTL；到期后点"通过"会因上下文过期而失败，但 run / `tool_call` 不自动置终态，容易积压无人处理。本次修复：新增 `AgentApprovalTimeoutScanner`（每 60s 扫描、默认超时 30 分钟），把超时 run 置为 `FAILED`、挂起的 `tool_call` 置为 `TIMED_OUT`。
- [x] Agent 工具调用全局硬上限：`executeLoop` 只按 LLM 轮数 `max_iterations`(10) 封顶，单轮可执行多个 toolCall、跨轮可反复调同一工具，副作用次数不受控。本次修复：新增 `rag2agent.agent.max-tool-calls`（默认 20），达到即走 `finalizeAtMaxSteps` 强制总结。
- [x] 异步入库中断任务恢复：应用在"任务已落库、消息未发送"或"处理中途崩溃"时，任务停在 `PENDING/PARSING/SPLITTING/EMBEDDING` 且无自动补跑；仅靠 MQ 重试 + 手动 `reingest`。本次修复：新增 `IngestRecoveryService`，启动全量 + 周期扫描非终态任务，带 Redis 文档锁检查后重置为 PENDING 并重新驱动；`INDEXED/FAILED` 不动。
- [ ] Embedding 缓存只管查询向量：`QueryEmbeddingCache` 的 key 版本化只覆盖"查询向量"；正文切片向量是入库时直接算好写进 pgvector，模型升级必须 `reingest` 重算，否则新旧模型混用。当前保持运维侧处理，可评估片段级缓存。
- [ ] 限流是固定窗口（`INCR+EXPIRE` 的 Lua），非令牌桶；窗口边界突发流量可能被允许/拒绝，如需平滑可评估令牌桶。
- [ ] 多租户当前仅"知识库 owner 级"隔离：靠 `knowledge_base.owner_user_id` + 各入口 `requireOwned` + 检索 SQL 的 `kb_id` 过滤，属应用层约定，DB 层无 RLS/冗余 tenant 强隔离；需产品/架构决策后再实施。

## 五、后续升级选型顺序

1. 真实环境验证 `A1-R` 的断线恢复和 RocketMQ/Jaeger 父子链路。
2. 根据实例规模评估 `A2-C`、`A3-D` 等生产化数据承载方案。
3. 在真实评测集上决定 `A1-F`、`A5-S`、`A6-M` 等增强策略是否值得引入。

## 六、横向比较

| 编号 | 推荐项 | 主要收益 | 主要代价 | 典型影响面 |
|---|---|---|---|---|
| A1 | A1-R | 快速恢复、避免重复执行 | 丢失增量内容 | SSE、前端、run 查询 |
| A2 | A2-L | 轻量调参 | 不支持多实例同步 | 配置、管理接口 |
| A3 | A3-S | 快速获得可解释成本数据 | 价格和 tokenizer 需维护 | AI 客户端、指标、账本 |
| A4 | A4-K | 覆盖所有副作用请求 | 需要幂等记录和结果语义 | API、数据库、对象存储 |
| A5 | A5-R | 保护下游、防止雪崩 | 高峰期直接失败 | 检索线程池、错误响应 |
| A6 | A6-R | 低成本建立风险基线 | 语义识别有限 | Agent 入口、审计、指标 |
| A7 | A7-P | 启动轻、演示快 | 与完整拓扑有差异 | Compose、README、脚本 |

选择时可以按这三个问题判断：

1. 是否需要多实例生产能力？需要则优先考虑 `A2-C`、`A3-D`、`A1-F`。
2. 是否更看重快速交付和低运维成本？是则优先考虑 `A1-R`、`A2-L`、`A3-S`、`A5-R`、`A6-R`、`A7-P`。
3. 是否有强审计、财务对账或安全合规要求？有则优先考虑 `A1-F`、`A3-D`、`A4-K`、`A6-M`。
