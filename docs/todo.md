## 三、确认轻量方案后可快速实现

以下项目本身不复杂，主要差异在接口语义、依赖和运维方式。请按编号选择；未选择前不改代码。

### 3.1 `A1` SSE 断线恢复协议

**问题**：当前能正确解析事件，但连接中断后不会自动恢复，已发送内容也没有断点语义。

**推荐：客户端重试 + 服务端 run 查询（A1-R）**

- SSE 首事件返回 `runId` 和 `traceId`，客户端断线后按退避重新请求 `GET /api/agent/runs/{runId}`。
- 服务端不缓存完整 token 流，不引入事件序号和重放队列。
- 优点：改动小、依赖少、不会重复执行工具，适合当前 Agent 已有 run 状态持久化的实现。
- 缺点：无法恢复到精确 token 位置；断线期间生成中的增量内容会丢失，客户端只能看到最终答案或阶段状态。
- 适用：单机 Demo、内部系统、对逐 token 连续性要求不高的场景。
- 实现代价：低，主要涉及 SSE 首事件、run 状态查询和前端退避重试。

**完整选项：事件序号重放（A1-F）**

- 每个 SSE 事件持久化 `eventId`，客户端带 `Last-Event-ID` 恢复，服务端重放缺口。
- 优点：可精确恢复事件顺序，用户体验接近不中断；便于审计和问题回放。
- 缺点：需要事件存储、过期清理、重放幂等和并发订阅控制；存储量、实现复杂度和运维成本明显增加。
- 适用：生产级长回答、移动网络不稳定、需要完整审计或断点续传的场景。
- 实现代价：高，需要新增事件模型或 Redis Stream，并定义事件保留时长。

### 3.2 `A2` 动态配置

**问题**：模型、重试、熔断、切块等配置当前重启生效。

**推荐：本地 YAML + 管理接口（A2-L）**

- 新增 `RuntimeConfigProvider`，内存快照覆盖 YAML 默认值。
- 仅允许白名单配置，变更带版本号并写审计日志；重启后回到 YAML。
- 优点：不增加外部组件，开发和部署最简单；配置变更链路清晰，适合当前单机 Demo。
- 缺点：多实例之间不会自动同步；重启后配置恢复默认，不能提供真正的发布、灰度和回滚能力。
- 适用：本地开发、单实例部署、临时调参和演示环境。
- 实现代价：低到中，集中在配置快照、白名单校验、版本记录和管理接口。

**生产选项：配置中心（A2-C）**

- 接入 Nacos/Apollo，支持发布、灰度、回滚和多实例同步。
- 优点：具备多实例同步、版本发布、灰度、回滚和变更审计能力，适合生产集群。
- 缺点：引入新的基础设施、权限体系和可用性依赖；本地开发、测试和故障排查复杂度上升。
- 适用：多实例生产环境、频繁调参、需要配置审批和灰度发布的场景。
- 实现代价：中到高，需要选定配置中心并补充 Docker、权限、启动顺序和回滚演练。

### 3.3 `A3` 真实 Token 计数与成本账本

**问题**：当前上下文预算使用保守估算，usage 只记录 token 数，不计算真实价格。

**推荐：provider tokenizer 适配器 + 静态价格表（A3-S）**

- 按 provider/model 实现 `TokenCounter`，不可用时保留估算并标记 `estimated=true`。
- 价格使用版本化 YAML 配置，记录 provider、model、tokenizerVersion、estimated/actual 和偏差。
- 优点：数据模型和依赖都轻量，能较快获得可解释的 token/成本数据；provider 数量少时维护成本低。
- 缺点：价格调整需要改配置并发布；tokenizer 仍可能因 provider 差异产生偏差，无法自动处理复杂计费规则。
- 适用：当前项目的少量 provider、单体部署和研发阶段成本观测。
- 实现代价：中，需要抽象 tokenizer、增加账本字段和补充价格配置及测试。

**数据化选项：数据库价格表（A3-D）**

- 增加模型价格表和生效时间，账本按价格版本计算成本。
- 优点：价格可由运营按生效时间调整，支持历史账本重算、多币种或不同计费规则扩展。
- 缺点：增加数据库迁移、管理接口、权限控制和价格版本冲突处理；数据模型更重。
- 适用：模型数量多、价格变化频繁、需要财务对账或多团队分摊成本的场景。
- 实现代价：中到高，除 tokenizer 和账本外还要建设价格管理闭环。

### 3.4 `A4` 统一 API 幂等键

**问题**：Agent 已支持 `clientRequestId`，上传、创建知识库等接口仍没有统一请求幂等语义。

**推荐：按接口定义 `Idempotency-Key`（A4-K）**

- 仅对创建/有副作用接口启用；以 `owner + endpoint + key` 建幂等记录，参数指纹不一致返回 400。
- 上传接口额外保存文件 checksum；相同 key 重放返回第一次结果，不重复发消息。
- 建议幂等记录 TTL 为 24 小时。
- 优点：语义完整，能覆盖网络重试、客户端超时和消息重复；参数指纹能阻止同一 key 被错误复用。
- 缺点：需要新增幂等记录、唯一约束、结果快照和清理策略；文件上传要处理对象存储与数据库的一致性。
- 适用：对创建、上传、扣费或异步任务重复执行敏感的生产 API。
- 实现代价：中，需要逐个梳理接口返回值和失败恢复语义。

**简化选项：仅 checksum 复用（A4-H）**

- 只按 `kbId + file checksum` 复用或创建新版本，不引入通用幂等表。
- 优点：实现快、数据结构简单，能有效减少相同文件重复上传和重复入库。
- 缺点：只覆盖文件内容，不覆盖创建知识库、评测任务等非文件请求；同一内容的不同业务意图无法区分。
- 适用：当前只想解决重复上传，且暂不承诺全 API 幂等的场景。
- 实现代价：低，但后续扩展到通用幂等时可能需要迁移。

### 3.5 `A5` 检索并行池背压

**问题**：向量/关键词召回已并行，但队列满时的策略和 P95 证据不足。

**推荐：快速失败（A5-R）**

- 队列满直接返回稳定 503/Retry-After，并记录 rejected 指标。
- 不扩大线程池，避免高峰期把数据库和模型服务拖垮。
- 优点：行为确定、保护下游最有效，线程池和数据库负载容易控制，故障可以快速暴露。
- 缺点：高峰期部分请求会直接失败，用户需要重试；对突发流量的容错能力较弱。
- 适用：请求可重试、优先保证系统不雪崩的生产服务。
- 实现代价：低，只需捕获拒绝异常、统一 503 响应和指标。

**降级选项：队列满时串行执行（A5-S）**

- 先执行向量召回，再补关键词召回；延迟更高但成功率更高。
- 优点：队列满时仍有机会完成请求，用户感知的失败率更低。
- 缺点：串行路径延迟更高，可能导致请求堆积；总超时、取消和结果标记逻辑更复杂。
- 适用：读请求优先、延迟可接受且召回成功率比尾延迟更重要的场景。
- 实现代价：中，需要扩展超时策略和降级指标。

### 3.6 `A6` 提示注入风险信号

**问题**：已有权限边界，但没有对“忽略系统指令、索取密钥”等输入做风险标记。

**推荐：规则引擎仅标记（A6-R）**

- 使用可配置关键词/正则，写入风险指标和审计字段，不自动拒绝请求。
- 无新增模型调用，误报可控，不能替代 ACL。
- 优点：零模型成本、低延迟、易解释，适合作为安全观测和后续治理的数据入口。
- 缺点：只能覆盖已知模式，容易漏报和误报；不能单独判断复杂的语义攻击。
- 适用：先建立风险基线、需要保守上线、不希望影响正常问答的场景。
- 实现代价：低到中，主要是规则配置、脱敏日志、指标和测试集维护。

**增强选项：分类模型（A6-M）**

- 使用独立分类模型判断风险并决定拦截/降级。
- 优点：对变体表达和复杂语义的识别能力更强，可按风险等级执行拦截、降级或人工审核。
- 缺点：增加模型成本和延迟，引入新的可用性依赖；误判会直接影响用户请求，需要持续评测。
- 适用：有稳定攻击样本、明确安全策略和专门安全运营能力的生产环境。
- 实现代价：高，需要模型选型、样本标注、阈值校准和故障降级。

### 3.7 `A7` 最小 Demo 部署

**问题**：当前 Compose 是完整集成拓扑，新机器启动步骤较多。

**推荐：Compose demo profile（A7-P）**

- 保留 PostgreSQL、Redis、MinIO 三项核心服务；RocketMQ、Neo4j、Jaeger 作为完整 profile。
- 增加 health/bootstrap 脚本和端口覆盖说明。
- 不承诺 Demo profile 支持异步入库和完整观测能力。
- 优点：新机器启动更快、资源占用更低，核心上传和检索链路更容易演示。
- 缺点：与完整生产拓扑存在差异，异步入库、消息链路、图能力和完整观测不能在 Demo profile 验证。
- 适用：开发体验、招聘演示、功能验收和低资源环境。
- 实现代价：中，需要维护 profile、健康检查和两套启动说明。

**单容器选项：应用 + 依赖说明（A7-D）**

- 不拆 Compose profile，只补一键脚本和故障诊断。
- 优点：改动最小，不产生两套服务定义和配置漂移问题；完整能力保持一致。
- 缺点：仍需启动全部中间件，首次启动慢、内存占用高，弱机器上失败概率更高。
- 适用：团队机器配置统一、完整拓扑本身就是验收目标的场景。
- 实现代价：低，主要是脚本、健康检查和错误提示。
