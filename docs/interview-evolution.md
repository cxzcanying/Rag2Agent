# V2 工程现状与演进方案（面试说明）

本文记录当前 V2 已落地能力、验证证据和后续升级路径；标注为“后续”的内容才是尚未接入的设计。

## 1. SSE 断线恢复

当前使用 Redis Stream 持久化结构化 SSE 事件，客户端携带 `Last-Event-ID` 回放缺口，按 run 权限校验后只返回后续事件；超出保留窗口时仍可通过 `runId` 状态查询获得最终结果。

## 2. 动态配置

当前使用本地 YAML 默认值加内存白名单快照，适合单机。多实例生产环境可迁移到 Nacos/Apollo，增加版本发布、灰度、回滚、权限审批和配置变更审计。

## 3. Token 与成本

当前按 provider/model 记录实际 usage 与估算值偏差，并写入可对账 usage 账本；价格支持版本、币种和缓存 token 单价配置。本项目选择 YAML/环境变量价格（A），原因是当前单体部署、模型数量少、价格随发布变更即可满足研发和演示需求；数据库价格表（B）会引入迁移、管理接口、权限、生效时间冲突和历史重算规则，在尚无财务对账要求时投入产出比不高。若后续需要财务审计、历史账单重算或多实例统一变更，再升级为 B。

## 4. API 幂等

当前对知识库创建、文档上传和评测任务支持 `Idempotency-Key` 或等价幂等键。后续可扩展到所有有副作用接口：以 owner、接口范围和参数指纹建立唯一约束，保存响应快照并设置过期清理任务。

### 为什么幂等边界放在 Agent 请求层

Agent 的幂等边界应放在“创建一次 Agent 执行请求”这一层，而不能只给 `delete_document` 之类的高风险工具加幂等。原因是一次用户请求并不等于一次工具调用：它可能先检索，再调用模型多轮决策，可能不调用工具，也可能调用多个工具，还可能在等待审批时暂停。客户端超时、SSE 断线、网关重试或用户重复点击时，服务端面对的是同一个业务意图，而不是一个已经确定的工具参数。

请求级幂等解决的是“同一个意图只创建一个 AgentRun”:

```text
clientRequestId
  -> (user_id, client_request_id) 唯一约束
  -> 已完成：返回保存的答案和引用
  -> 执行中：返回已有 runId/状态
  -> 未创建：只创建一次 AgentRun
```

这样做有四个直接收益：

1. **覆盖没有工具调用的请求。** 普通问答也会因为网络重试而重复执行；只在删除工具上做幂等，无法避免重复检索、重复 LLM 调用和重复 token 成本。
2. **覆盖模型决策过程。** 工具名称和参数是在 LLM 运行过程中才产生的，请求入口并不知道最终会不会调用工具。把幂等放在入口，才能覆盖“无工具、一个工具、多个工具、先审批后工具”等所有分支。
3. **保证断线恢复不重复启动。** SSE 只负责传输事件，断线后前端用同一个 `clientRequestId` 重试并取回原来的 `runId`。如果只给删除工具去重，重试会先创建第二个 AgentRun，可能产生第二条审批记录。
4. **控制整条链路的成本和状态。** 检索、上下文压缩、模型调用、工具审批、轨迹记录和成本账本都属于一次 Agent 执行；请求级去重可以避免这些步骤整体重复。

请求级幂等和工具级幂等不是二选一，而是两层防线。请求级幂等负责把网络重试合并到同一个 AgentRun；工具级幂等仍应保护删除、写入等副作用操作，防止审批恢复、消息重试或其他入口在工具执行阶段重复产生外部效果。Redis session 锁也不能替代请求幂等：锁只能阻止同一时刻的并发执行，锁释放后的延迟重试仍需要通过 `clientRequestId` 识别为同一个请求。

面试中可以概括为：**Agent 的不确定性发生在请求内部，幂等键必须覆盖整个状态机；工具幂等是副作用保护，请求幂等是业务意图去重。**

### Agent 会话锁增强及效果

Agent 执行期间还需要一把按 `userId + sessionId` 划分的 Redis 会话锁，避免同一会话被多个请求同时推进。增强后的实现使用随机锁令牌执行 `SETNX`，锁 TTL 为 30 分钟，并由后台任务每 10 分钟用 Lua 脚本续租；续租和释放脚本都会先比较令牌，只有锁的持有者才能修改或删除对应 Key。finally 代码块负责停止续租并释放锁，同时把续租丢失、续租异常和释放异常记录到 `rag2agent.lock.operations` 指标。

它带来的效果是：

1. **拦截同一会话的并发执行。** 用户快速连续点击、浏览器重复提交或两个网关请求同时到达时，只有第一个请求进入 Agent 状态机，后续请求快速返回“该会话已有请求正在执行”。
2. **覆盖长耗时链路。** 检索、多个 LLM 轮次和工具执行可能超过普通短 TTL；续租避免锁在任务仍运行时过期，降低两个请求交错写入消息历史、状态和审批记录的风险。
3. **避免误删他人的锁。** 令牌比较保证旧请求即使因为网络抖动或续租失败，也不能删除后来请求重新获得的锁。
4. **让锁故障可观测。** 续租丢失、Redis 异常和释放失败都有独立指标，便于区分真实并发冲突与基础设施问题。

会话锁解决的是“同一时刻不能并发执行”，请求幂等解决的是“同一个业务意图在不同时间重试仍只执行一次”。两者必须同时存在：请求结束后锁会释放，之后的延迟重试仍要依靠 `clientRequestId` 找回原来的 AgentRun。

## 5. 检索背压

当前检索线程池队列满时快速失败并返回 503。若业务更看重成功率，可增加串行降级分支；若流量继续增长，则应在网关层限流、按知识库设置配额，并通过压测数据校准线程池容量。

## 6. 中文关键词检索

D13 中文评测已证明当前 `pg_trgm` 关键词路是短板：MIRACL zh 100 条用例中，`KEYWORD` 的 Hit@5/MRR 均为 `0.010`，而 `VECTOR` 为 `1.000/0.955`；关闭或开启 rerank 对关键词召回没有实质改善，说明根因是分词/召回而不是精排。

当前已落地 PostgreSQL 分词扩展路线（B，`zhparser`）：数据规模仍小、主数据和权限过滤都在 PostgreSQL，无需新增索引同步链路。自定义镜像 `rag2agent-postgres:pg17-zhparser` 已构建成功，并在保留现有数据卷的前提下启用；同一 MIRACL zh 100 条子集、相同 topK/candidateTopK 下，`KEYWORD` Hit@5/MRR 从 `0.010/0.010` 提升到 `0.190/0.180`（Run 15），`HYBRID` 为 `1.000/0.912`（Run 16）。默认 Compose 仍使用官方 `pgvector/pg17`，通过 `RAG2AGENT_POSTGRES_IMAGE` 显式切换扩展镜像；二元切分（A）保留为零依赖回退基线。

验收结论：关键词路 Hit@5 已明显高于 `0.010`，混合检索 Hit@5=`1.000` 高于现有 AUTO `0.660`，因此接受 `zhparser` 作为当前中文关键词实现。后续只有在数据规模或运维边界变化时再评估 OpenSearch。

## 7. 提示注入防护

当前仅使用规则标记风险，不替代权限校验，也不自动拦截。后续可用脱敏攻击样本训练或选择分类模型，按风险等级执行告警、降级和人工审批，并持续评估误报/漏报。

## 8. Demo 与生产拓扑

当前 Compose 默认启动 PostgreSQL、Redis、MinIO；未启用 RocketMQ 时上传会复用同一条 Pipeline 同步入库，完整异步拓扑通过 `--profile full` 和 `RAG2AGENT_MQ_ENABLED=true` 启动。生产环境仍需补充独立配置、密钥管理和备份恢复策略。

## 面试回答主线

先用最小实现满足可靠性边界，再用指标和真实流量决定是否升级：事件回放解决 SSE 增量恢复，配置快照解决单机调参，provider 适配器解决模型差异，幂等记录解决网络重试，快速失败保护下游，规则标记建立安全基线，Compose profile 降低上手成本。每次升级都保留回退路径，避免为了“未来可能需要”提前引入高运维依赖。
